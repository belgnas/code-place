# tech-doc — 技术栈学习文档整理

## 目的

用户是一名以**学习为核心目的**的开发者（做项目只是学习的工具）。每当用户接触到一个新技术栈、新框架、新工具或一个重要的新知识点时，把它整理成一份**完整、教程级、可复刻**的中文 markdown 技术文档。

核心原则：**不要只讲当前项目里用到的那一小部分。** 要覆盖该技术栈的完整知识体系，让用户仅凭这一份文档就能系统地学通、甚至独立复刻。

## 何时触发

- 用户说「我学到了 X」「刚学了 X」「把 X 整理成文档」「总结一下 X」「遇到新知识点了」。
- 用户在做项目过程中引入并使用了一个此前仓库里没有系统文档的技术（如某个框架、库、协议、工具链、语言特性）。
- 用户的 CLAUDE.md 提示「遇到新知识点就调用这个 skill」。

不确定用户想要哪个技术栈时，先问清楚「你想让我整理哪个技术栈/知识点」，再动手。

## 存放位置

- 默认存放在**当前工作目录**下（用户偏好）。
- 文件名用该技术栈的中文或通用英文名，如 `Docker入门到实践.md`、`XPath语法详解.md`、`React核心概念.md`。
- 与仓库现有命名风格保持一致（中文优先，专有名词用英文）。
- 若当前目录已存在同名文档，**更新补全**而非新建重复文件。

## 文档深度：完整教程级

每份文档应尽可能自成体系。默认包含以下结构（按技术栈实际情况裁剪，但不要因为「项目没用到」就省略核心知识）：

1. **概述** — 这是什么、解决什么问题、适用场景、与同类技术的对比。
2. **核心概念与原理** — 底层模型/工作机制，不只是「怎么用」，还要讲「为什么这样设计」。
3. **环境搭建 / 安装配置** — 从零开始，含常见平台（尤其 Windows，用户主力环境）。
4. **基础语法 / 基础用法** — 系统覆盖，配可运行的最小示例。
5. **进阶特性** — 项目里没用到但属于该技术核心的部分也要讲（这是重点）。
6. **实战示例** — 结合用户当前项目的真实用法举例，帮助迁移理解。
7. **常见坑 / 易错点 / 最佳实践** — 踩坑经验、性能与安全注意事项。
8. **速查表 / 命令表 / API 表** — 便于日后快速回顾。
9. **延伸学习** — 进一步的方向、官方文档链接、推荐资源。

## 写作要求

- **中文优先**：正文用中文，代码标识符、命令、专有名词保留英文。
- **完整可运行**：代码示例尽量完整、可直接运行，配必要注释；说明预期输出。
- **由浅入深**：从概念推导到实践，照顾零基础也能跟上。
- **准确**：涉及版本差异、平台差异（Windows/Linux）时明确标注。不确定的内容先查证（可用 WebSearch/WebFetch 核实官方文档），不要臆造 API。
- **风格一致**：与仓库内现有 markdown 文档的排版、标题层级、代码块风格保持一致。
- **善用表格与代码块**：速查内容用表格，语法/命令用代码块。
- **复杂度分析**（若是算法/数据结构相关）：给出时间/空间复杂度。

## 工作流程

1. 确认要整理的技术栈/知识点（不明确就问）。
2. 快速了解用户在当前项目里是怎么用它的（读相关文件），作为「实战示例」一节的素材。
3. 判断该技术栈的完整知识边界 —— 主动补齐项目未覆盖但属于核心的内容。必要时查证官方资料。
4. 按上面的结构写出完整文档，存到当前工作目录。
5. 简要告诉用户文档路径和它覆盖了哪些章节，提示哪些是「项目外补充」的知识点。

## 反面案例（不要这样做）

- ❌ 只把项目里出现的那几个函数/命令列一下就交差。
- ❌ 泛泛而谈没有可运行示例。
- ❌ 用大量英文正文（用户要中文）。
- ❌ 编造不存在的 API 或版本行为。
